# 概念

Forgeyard 的各個部分怎麼搭在一起，依照你會碰到的順序說明。每一節都會講這是什麼、它幫你做什麼，以及要注意的地方。

## 機器與 agent

**機器**是 Forgeyard 可以在上面執行工作的任何電腦：GPU 伺服器、工作站，或只有 CPU 的電腦。每台機器都執行一個 **agent**（代理程式），這是一支小程式，它會：

- 回報機器的硬體：每張 GPU（型號、記憶體、驅動程式、負載、溫度）、CPU 和 RAM；
- 和伺服器保持一條連線，而這條連線是**由 agent 發起**的：伺服器永遠不需要主動連到機器，所以就算機器在防火牆或 NAT 後面，只要它連得到伺服器就能運作；
- 啟動、監看並停止伺服器要求它在這台機器上執行的東西。

機器只需要**加入**一次，使用從 **機器** → **加入機器** 取得的**加入權杖**（join token）：它只能用一次、15 分鐘內有效，伺服器只保留它的雜湊值。agent 會用它換到這台機器自己的**憑據**，存放在 agent 的狀態目錄（`/var/lib/forgeyard-agent`，權限 0600）。之後啟動就不再需要權杖。

agent 只透過伺服器的**憑證授權單位**（CA）來信任伺服器，並以加入指令裡的指紋釘選這個 CA：中間如果有別的機器拿著其他憑證，會被拒絕。請看[信任 CA](quick-start.md#2-create-the-owner-and-trust-the-ca)。

agent 連線中時，機器顯示 **線上**；超過 30 秒沒有收到任何訊息時，顯示 **離線**（agent 每 10 秒送一次心跳）。agent 會自己重新連線。管理員可以**撤銷**一台機器（它的憑據立刻失效），或把它**移除**。

機器離線期間，請求不會再送到它上面的副本。離線超過 **10 分鐘**（`AGENT_OFFLINE_MOVE_SECONDS`）時，它上面部署的副本會依部署自己的規則，重新放到放得下的機器上；**固定（pinned）**在那台機器上的部署會等它回來。機器回來時，它的 agent 會停掉已經搬走的東西。請看[機器一直離線時](how-to.md#when-a-machine-stays-offline)。

停止或重新啟動 agent **不會停掉它的模型和應用程式**：重新啟動的 agent 會找到它們並接手管理。這就是安裝的服務使用 `KillMode=process` 的原因。

agent 從 `/etc/forgeyard/agent.toml`、`FORGEYARD_*` 環境變數和命令列旗標讀取設定（[完整列表](reference.md#agent-settings)）。

**機器** 頁面每台機器一張卡片，並用圖示標出它的種類：**NVIDIA GPU**、**AMD GPU**、**AMD APU**（和系統共用記憶體的 AMD GPU，例如 Radeon 8060S）或 **僅 CPU**。它的每張顯示卡是一排由下往上填的格子：先是 Forgeyard 保留的量，再來是其他用量（顯示卡上的其他程式，以及沒有宣告記憶體的 Forgeyard 應用程式），最後是可用的量。卡片也會顯示可用記憶體、在上面執行的部署和應用程式數量，以及它們的名稱。卡片上方的摘要計算每種機器各有幾台，以及離線的有幾台：*1 NVIDIA machine*、*2 CPU-only machines*（算的是機器，不管它有幾張卡）。點進一台機器就是它自己的頁面：**記憶體配置圖**（memory map）把每張卡依佔用者分段，標出名稱和保留量；另外還有在這台機器上執行的東西、GPU 存取權與 runtime，以及 agent 的資訊。管理員也在這裡撤銷或移除機器。

## GPU 存取權

預設情況下，Forgeyard 可以使用機器上的每一張 GPU。如果機器要和其他人或其他程式共用，管理員可以在機器的頁面（**機器** → 該機器）→ **變更 GPU 存取** 選擇 Forgeyard 可以用哪些卡。不在清單上的卡，絕不會分配給 Forgeyard 執行的任何東西。

- 分配給獨占副本的 GPU 只屬於那個副本。
- 共用一張卡的副本（嵌入模型、重排序模型、語音轉文字預設都是）只能使用自己保留的記憶體量，所以一張卡可以放好幾個。
- 記憶體以卡片當下回報的**可用**量為準，所以別人正在用的記憶體會被扣除，另外再保留一段安全餘裕（512 MiB）。
- 行程只會在 `CUDA_VISIBLE_DEVICES`（NVIDIA）或 `ROCR_VISIBLE_DEVICES`（AMD）裡拿到自己那幾張卡的 ID；容器也只會被傳入自己的卡。正在使用中的卡不能從清單中移除。

## GPU 共用

每個 GPU 部署不是 **獨占** 就是 **共用 VRAM**：

- **獨占** 是對話 recipe 的預設：每個副本拿到整張卡，Forgeyard 不會在上面放其他東西。模型可以用到整張卡的算力。
- **共用 VRAM** 是嵌入、重排序和語音轉文字的預設：副本只保留估算的記憶體量，其他共用的副本可以放進卡上其餘的空間（vLLM 也會被告知只用那麼多）。同一張卡上的副本共用算力，所以負載高時每個都會回應得慢一些。

獨占的副本和共用的副本絕不會用同一張卡：兩邊都必須共用。Forgeyard 會在共用有幫助時提醒：

- 獨占的模型只需要它那張卡一半以下的記憶體時，部署和修改頁面會說明（*This model needs 14.38 GiB of an 80.00 GiB card; with Share VRAM the rest can hold other models*）；
- 記憶體其實夠、只是被獨占擋住時，拒絕訊息會寫 *fits if both share VRAM*，並說出佔著那張卡的副本；
- **Setup health** 會為保留不到 24 GiB 以上卡片一半記憶體、正在執行的獨占副本提供一則說明（`deployment-could-share`）。

要在部署上修改，用 **編輯**：[修改部署](how-to.md#change-a-deployment)。

## 應用程式（已淘汰）

1.4 之前，主控台也能執行**應用程式（app）**：你自己的程式（容器或行程、服務或一次性任務），跑在你的機器上，也可以公開在 `/x/<name>` 讓 API 金鑰呼叫。Forgeyard 的重點是執行和管理模型，所以 1.4 起應用程式離開主控台，**1.5 會移除**它們：API 裡屬於應用程式的部分（`/api/workloads`）、範本，以及閘道的 `/x/`。在那之前，它們只能透過 API 使用，並會明白告知：每個回應都帶 `Deprecation` 標頭，伺服器紀錄會警告（每小時最多一次），只要還有任何應用程式，**Setup health** 就會警告。細節在[參考資料](reference.md#apps-deprecated)。

- 要提供模型，請在 **服務中** 部署它。物件偵測、影像分割和深度估計從 1.4 起是[視覺模型](#vision-models)。
- 內建引擎跑不了的模型，可以加一個**自訂引擎**（**Models → Engines → Add a custom engine**）：和內建的一樣是一份 recipe，指向它的容器映像檔或程式。

**機器** 仍會列出佔用顯示卡的應用程式名稱，所以使用中的卡不會被顯示成空閒。模型部署也以 workload（runtime 為 `model`）執行：模型就是這樣跑的，這部分沒有淘汰。

## 模型、引擎與估算

模型放在兩個頁面。**服務中** 是現在正在執行的：依種類（chat、多模態 chat、嵌入、重排序、文字分類、語音轉文字、文字轉語音、圖片、影片、視覺）把部署分組，每組標出它在 `/v1` 底下回應的路徑，每個部署一行：在哪裡執行（機器和顯示卡）、記憶體和狀態。**部署模型** 也在這裡，每個部署的頁面在 `/serving/<id>`。有[雲端備援](#cloud-providers-and-tiers)的部署會標出它的供應商，例如 *→ Gemini*；備援本身在部署的頁面上。

**Models** 是模型庫，也就是可以部署的東西，分成三個分頁：**Catalog**（目錄，預設）、**Engines**（引擎），以及管理員才有的 **Sources**（來源）。雲端模型和供應商在 **雲端** 頁面（管理員）。1.3 的連結（`/models/deployments/<id>`、`/models/deploy`、`/models?tab=routes`、`/models/routes/<id>`、`/providers`）會打開新的位置。

- **目錄**列出你可以部署的模型。管理員可以從**推薦**清單、**Hugging Face 搜尋**，或從某個來源加入模型：`hf://org/name`、一個 GGUF 網址，或用 `local://` 指向機器上的某個目錄。加入模型時只會讀取它的資訊，不會下載。每一列都有 **Deploy** 和 **Download to…**。
- **模型的用途**來自它在 Hugging Face 上的任務，再用它的 `config.json` 核對。很多 reranker 標的是 *text classification*，文字分類模型也是；用 vLLM 的規則分辨：只有一個輸出（`num_labels` 為 1：bge-reranker、ms-marco 的 cross-encoder）是 reranker，兩個以上標籤（情緒、語言、有害內容）是[文字分類模型](#text-classification)（1.4.4），絕不會被當成 reranker。語言模型型的 reranker（例如 Qwen3-Reranker）不受影響。
- **引擎**（engine）描述某一類模型要怎麼執行：用哪個程式、哪個容器映像檔（以 digest 釘選）或發行版本、哪些參數，以及需要多少記憶體。API 和 YAML 檔案稱它為 **recipe**（配方；`/api/recipes`、`forgeyard/recipes/*.yaml`）；管理員在 **Engines** 分頁加入自訂的。內建的有：`vllm`（NVIDIA 和 AMD 上的對話模型）、`vllm-pooling`（嵌入、重排序與文字分類）、`llama-cpp`（NVIDIA、AMD（ROCm 或 Vulkan）或 CPU 上的 GGUF）和 `faster-whisper`（語音轉文字）。
- 目錄裡的每個模型都有**自己的頁面**（1.4.3），點它的名稱就會打開：`/models/<name>`。頁面上有模型的資訊（來源與版本、授權、任務、架構）、**哪些機器的模型快取裡有它**、用引擎的預設值現在**放不放得下**每台機器、它的部署、能執行它的引擎，以及它的檔案和大小。每個引擎也有自己的頁面 `/models/engines/<name>`：它的變體（每種硬體用的映像檔或程式，以及是否以 digest 釘選）、**哪些機器已經有那個映像檔或程式**、它的參數，以及使用它的部署和模型。主控台裡所有模型和引擎的名稱都連到這些頁面。管理員可以在模型頁面設定**顯示名稱**；模型的名稱本身不變，因為部署記錄的是它，所以 `deploy`、`deployments`、`routes`、`engines`、`catalog`、`sources`、`recommended`、`search` 和 `inspect` 不能當模型名稱。（[查看模型或引擎](how-to.md#look-at-a-model-or-an-engine)）
- **Sources**（管理員）說明模型可以從哪裡來：GGUF 網址允許的主機、`local://` 模型的目錄，以及伺服器的 Hugging Face 權杖。
- **估算**是一份副本需要的記憶體：權重、依你選的上下文長度和並行數計算的 KV cache、引擎本身的額外開銷、CUDA context，以及能讀圖片的模型的視覺編碼器。部署頁面會在下載任何東西之前，逐項顯示估算結果和放得下的位置。KV cache 依每一層實際保存的內容計算（1.4.5）：滑動視窗層（Gemma、gpt-oss、Mistral 7B）最多只存視窗長度（vLLM 上再加兩個處理中的步驟，每個 2,048 個 token，Gemma 4 是 2,496；配方會明確傳這個值，所以每張卡都一樣），MLA 模型（DeepSeek、Kimi）每個 token 只存一個壓縮的 latent，混合模型（Qwen3-Next、Granite 4、Falcon-H1）只有注意力層會隨上下文長度增加，另外每個請求有固定大小的 *Recurrent state*。留在 CPU 上的 GGUF 層也會在那台機器的 RAM 預留記憶體；每次放置副本時，部署的估算都會依引擎目前的設定重新計算。
- 每台機器上的**模型快取**（以 root 執行的 agent 預設是 `/srv/forgeyard-models`）保存下載下來的檔案，檔案會以 checksum 檢查，並由這台機器上的所有副本共用。容器會以唯讀方式掛載自己的模型。機器的頁面會列出快取裡有什麼和大小，並可刪除那台機器上沒有部署在用的項目（[釋出機器上的磁碟空間](how-to.md#free-disk-space-on-a-machine)）。**Download to…** 可以在部署之前先把模型和引擎放進去（[部署之前先下載模型](how-to.md#download-a-model-before-deploying-it)）。連不到 Hugging Face 或 GitHub 的機器會**經由伺服器**取得檔案，伺服器只轉送、不存檔；agent 會像檢查任何下載一樣檢查它們。1.4.1 起，模型檔會先從快取裡已經有它的另一台機器取得（仍然經由伺服器），之後才用網際網路。有釘選的引擎映像檔也會這樣一層一層送過去，管理員也可以從機器的頁面上傳任何映像檔，或從另一台機器的引擎複製映像檔（1.4.1）；完整流程請看[讓沒有網路的機器執行模型](how-to.md#run-a-machine-without-internet-access)。模型在不在某台機器上，一律以它的 agent 回報的為準，所以手動複製過去的模型也算。
- **受限（gated）**的 Hugging Face 模型需要一個接受過它授權條款的帳號的權杖。伺服器保存**一個 Hugging Face 權杖**（管理員在 **Models → Sources** 設定，加密儲存），用來檢查和下載這些模型；部署也可以帶自己的權杖，對該部署優先使用。

## 部署與閘道

**部署**用一個引擎（recipe）執行一個模型，包含一個或多個副本。它的副本以 runtime 為 `model` 的 workload 執行，只在部署的頁面上看得到（不在 **Apps**）。Forgeyard 會：

1. 把每個副本放到放得下的地方。在放得下的機器之間，依序比較：
   - 過去一小時內**連不到**這個副本在那裡要下載的來源（模型的主機，例如 huggingface.co；引擎壓縮檔的主機，例如 github.com；或映像檔的 registry，例如 ghcr.io）的機器排在最後：只有其他機器都放不下時才會用它。名稱解析失敗、連線被拒或逾時、網路無法連線，才算「連不到」；HTTP 錯誤、權杖被拒或磁碟已滿則不算。agent 能**經由伺服器**下載的機器（1.4；它的 **下載時的網路連線** 是 **自動** 或 **一律經由伺服器**）會改用這個方式取得模型、引擎壓縮檔和有釘選的引擎映像檔，所以不會因此被避開（[經由伺服器把模型送到離線機器](how-to.md#give-an-offline-machine-models-through-the-server)）；
   - 盡可能把同一個部署的副本放在**不同機器**上；
   - 已經**快取了這個模型**的機器優先，其次是也已經有引擎的機器（process 引擎執行的壓縮檔，或容器引擎執行的映像檔）；
   - 然後是夠大的卡中最剛好的那張（讓整張空著的卡留給大模型）；
2. 副本在原本的機器上下載時**連不到來源**（在那裡停在 backoff）時，把它重新放到另一台放得下的機器上：這台機器會被記住一小時，視為連不到那個主機。指定了機器的部署會留在那台機器上繼續重試。副本會在部署的頁面上說明原因：*cpu-01 could not reach huggingface.co; placed on cpu-02 instead*；
3. 如果哪裡都放不下，就拒絕這個部署，並逐台機器說明原因和差多少；
4. 在那台機器上下載模型（如果引擎的映像檔還不在，也會拉取它）、啟動引擎，並等到它變成健康狀態。部署的頁面會顯示下載和拉取的進度；刪除部署會立刻停止這兩者。

每個就緒的部署都以它的模型名稱，在 **`https://<server>:7860/v1`**（也就是**閘道**）以 OpenAI API 提供服務：`/v1/models`、`/v1/chat/completions`、`/v1/completions`、`/v1/embeddings`、`/v1/rerank`、`/v1/score`、`/v1/audio/transcriptions` 和 `/translations`，以及 Forgeyard 自己的 `/v1/classify`（文字分類）。`/v1/models` 列出你的金鑰可以用的模型；部署停止後，它會從清單消失，直到再次啟動為止，除非它的路由能把請求送到你的金鑰可以用的雲端供應商。

閘道會把每個請求送到正在處理中請求數最少的就緒副本；如果某個副本沒有回應，就改送下一個。副本無法繞過閘道直接使用：每個副本都有一把只有閘道知道的內部金鑰，agent 會拒絕送到副本連接埠的其他所有請求。

從 1.4.5 起，閘道和副本之間的流量都會**加密**：agent 以 TLS 提供副本的連接埠，憑證由 Forgeyard 的 CA 替那台機器簽發（金鑰由 agent 自己產生，絕不離開那台機器），有效 30 天，agent 會在到期前 10 天自動更新，不必重新啟動。閘道連某台機器時只接受那台機器的憑證，所以內部金鑰、提示詞和回答都不會以明文經過網路。比 1.4.5 舊的 agent 會繼續以純 HTTP 提供服務：**Setup health** 和它的機器頁面會顯示 *Traffic to <machine> is not encrypted: update the agent*（[更多](troubleshooting.md#traffic-to-a-machine-is-not-encrypted)）。1.4.5 的 agent 絕不會被以純 HTTP 連線：沒有有效憑證時連不到它的副本，Setup health 會顯示錯誤（[做法](troubleshooting.md#a-machine-has-no-certificate-for-its-replicas)）。

**Playground** 讓你以自己的身分、不需要 API 金鑰，透過同一個閘道試用模型。一個 **Model** 選單列出已就緒的模型，像 **服務中** 一樣依種類分組，用同樣的名稱和圖示（Chat、Multimodal chat、Embeddings、Rerank、Text classification、Speech to text、Text to speech、Images、Video、Vision）；選一個就會開出它的面板：對話（串流，能讀圖片的模型也可以附上圖片）、嵌入、重排序、文字分類（輸入文字，每段文字的各標籤機率以長條顯示）、語音轉文字、**Speak**、**Image**、**Video**，或視覺面板（送一張圖片，得到方框、遮罩或深度圖）。網址會記住選的模型（`/playground?model=<name>`）；1.3 的 Vision 分頁網址（`/playground?tab=vision`）會開出第一個就緒的視覺模型，沒有時就打開選單。沒有任何就緒的模型時，頁面會這樣說明，並指向 **Models → Catalog** 去部署一個。它的請求在 Usage 裡算作 `console`；它的雲端設定對管理員是 **Allowed**，對其他人則是他們能替自己金鑰設定的最大值。

## 閒置時休眠

從 1.5.0 起，部署可以在**沒人使用時休眠**：在它的*閒置時間*內沒有任何請求，它的副本就會像按下 **停止** 一樣停止，原本占用的 GPU 記憶體（或 RAM）讓給其他部署使用。模型檔案留在機器的模型快取裡，引擎映像檔也留在機器上，所以再次啟動時不需要重新下載。這個功能**預設關閉**，1.5.0 之前建立的部署和新的部署都一樣；開啟後，閒置時間預設是 **30 分鐘**，也可以自己設定（1 到 1,440 分鐘）。修改這兩個設定都不會重新啟動任何東西。

- **什麼算是使用：**閘道收下的每個送給這個模型的請求，不論來自哪把金鑰或 Playground（包括之後轉到雲端分層的請求，以及在佇列、圖片佇列中或等模型喚醒時等待的請求）、要求生成的影片，以及 *Try it*。`/v1/models`、健康檢查、主控台的頁面，以及輪詢影片工作的狀態都不算；閘道當場拒絕的請求也不算（部署已停止、無法喚醒、沒有目標服務這個端點）。
- **什麼時候休眠：**在閒置時間內都沒有請求時。閒置時間從最後一個請求起算，或從部署啟動、修改或變成就緒的時間起算，取比較晚的那個。有請求正在處理、有副本正在啟動、修改正在重新啟動它的副本，或者（影片）有工作在等待或生成中、有完成的影片還能下載（副本停止後影片就會遺失）時，都不會休眠。伺服器每 30 秒檢查一次。
- **伺服器重新啟動後**，所有閒置時間都從重新啟動時起算：最後一個請求的時間只記在伺服器的記憶體裡，所以重新啟動絕不會讓模型提早休眠。
- **休眠不是停止。**休眠中的模型仍然列在 `/v1/models` 裡，**下一個請求就會喚醒它**（見下方）；按 **啟動**（在它的頁面或 Playground 上是 **立即喚醒**）也會。如果原本的機器還有空間就回到那台機器，有指定機器時就回到指定的機器。對休眠中的部署按 **停止** 會讓它變成停止：之後請求會回應它已停止、不會喚醒它，它也會像以前一樣從 `/v1/models` 消失。
- **休眠時它的記憶體是空出來的**，其他部署（或者在共用的卡上，Forgeyard 以外的程式）可能會用掉它。這時它會在放得下的其他地方啟動，或像其他副本一樣等待空間。
- 進入休眠會記錄在部署的事件裡（*Asleep: no requests for 30 min; frees 14.4 GiB on gpu-01 GPU #4*），不會記在稽核紀錄：這不是某個人做的。用 Start 喚醒則會像一般啟動一樣被稽核；被請求喚醒會記成事件 *Woken by a request (key laptop)*。

### 收到請求時喚醒

送給休眠中模型的請求會喚醒它，模型就緒後客戶端就會拿到回應：

- **只喚醒一次**，不論同時來了多少請求：第一個喚醒它，其他請求看到喚醒已在進行。
- **請求會等待**，先到先服務，最多等部署的*喚醒時等待*（`wake_wait`，預設 **5 分鐘**，10 秒到 30 分鐘）。等待期間不會送任何東西給客戶端：回應（包括串流）以模型自己的狀態開始，所以客戶端看到的是正常的 200 或真正的錯誤，只是晚一點。
- **可以使用雲端分層的金鑰**（cloud 是 `fallback` 或 `on`），在有雲端分層的路由上，等待期間由雲端服務（`X-Forgeyard-Spilled: waking`），模型就緒後再回到本地。供應商會弄丟的結構化輸出絕不轉出去，而是等待。雲端目標失敗、或預算用完的請求，也會等本地模型。
- **無法喚醒時**（現在沒有機器有空間、指定的機器離線、引擎啟動失敗），請求會立刻得到 **503 `cannot_wake`** 和原因，不會白等 5 分鐘。它仍保持喚醒狀態，有空間時就會啟動，或在閒置時間後再次休眠；下一個請求會再試一次。
- **等待時間用完時**，回應 503 **`model_waking`** 和 `Retry-After`：它上次啟動花的秒數減掉已經過去的時間（至少 5 秒）。
- 放棄等待的客戶端會離開隊伍；喚醒會繼續。速率限制只在請求到達時計算一次。
- 依前面的客戶端選擇 `wake_wait`：如果前面有 60 秒就切斷請求的 proxy，就要設短一點（它會拿到 `model_waking` 可以重試），或加上雲端分層，或關閉休眠。
- **在主控台裡**：部署和修改表單的 *When not in use* 底下有這個設定（等待時間在 Advanced 裡），並寫出上次啟動花了多久（大約就是休眠後第一個請求要等的時間）；Serving 會顯示 **休眠中**（月亮圖示）和 **喚醒中**；部署頁面有 *When not in use* 卡片和 **立即喚醒**；Playground 的選單裡仍有休眠中的模型，請求等待時會顯示 *Waking the model (about 74 s)…*；Machines 會在休眠中的部署會執行的那台機器底下列出它；設定顧問會提醒佔著 GPU 記憶體、3 天沒人用的部署，以及一天被喚醒超過 10 次、啟動又要超過一分鐘的部署。

## 自動副本數

從 1.5.0 起，部署的副本數可以**跟著負載變化**：在部署或修改表單把 **副本** 設為 **依負載自動調整**，再設定最少和最多幾個。這個功能**預設關閉**，1.5.0 之前建立的部署和新的部署都一樣；開啟後，沒有另外設定時是 **1 到 2** 個（可設 1 到 16）。修改這些設定不會重新啟動任何東西。

- **負載**是閘道看到的這個部署的量：正在它的副本上處理的請求（不含正在排空的副本：那些請求會在那裡做完），加上在閘道的隊伍裡等它空位的請求（圖片還加上它的佇列）。同一個路由分層有好幾個部署共用一條隊伍時，每個部署各算一份。一個副本在**目標**下能承擔它的 *Concurrent requests*，預設是 80%：*Concurrent requests* 為 1 的副本是 0.8 個請求，為 4 的是 3.2 個。沒有這個設定的 recipe（語音轉文字、視覺）每個副本算 1 個請求。
- **多一個副本**：過去一分鐘的負載高於就緒副本在目標下能承擔的量時，或是達到它的**兩倍**時立刻（大約 10 秒內）加。**一次只啟動一個副本**：等它就緒才考慮下一個。而且**只在現在放得下的地方**加（有空間的線上機器；固定機器的部署只放在那台機器上）；Forgeyard 不會加一個要等空間的副本。放不下時，部署頁面會說明：*Wants 3 replicas, room for 2: …*，並列出每台機器的原因。
- **少一個副本**：在 **10 分鐘**內少一個副本也能在目標下承擔負載時（所以部署不會在一個和兩個之間來回跳），而且不會在一陣突發、少一個馬上又要加回來時移除。最新的副本會**先排空**：閘道不再送新請求給它，它正在處理的請求會做完（長的串流也一樣），之後才移除，由它的 agent 停止。如果這段時間負載又升高，或其他副本不再就緒，它會被留下。
- **會暫停**：修改正在重新啟動副本時、某個副本所在的機器離線時（它的副本可能會被搬走，見[機器一直離線時](how-to.md#when-a-machine-stays-offline)），以及部署啟動、被喚醒或修改後的 2 分鐘內。等休眠中的模型喚醒的請求不算進負載：喚醒本來就會啟動它的副本，等有副本就緒，這些請求就會像其他請求一樣被處理並計入。
- **執行中至少 1 個。**開啟[閒置時休眠](#sleep-when-idle)時，最少可以設 0：部署只會透過休眠（整個部署，在閒置時間之後）降到 0 個副本，喚醒時回到它的最少值（至少 1 個）。
- **影片部署永遠不會自動調整副本數：**影片工作屬於製作它的那個副本。
- 新副本啟動期間（小的 vLLM 模型大約一分鐘），請求和以前一樣在閘道的隊伍裡等；可以使用雲端分層的金鑰，在所有本地副本都忙時也和以前一樣轉到雲端。*Wait for the first answer* 一樣是從請求送到副本時開始算。
- 每個決定都是部署的一個事件（*Scaled up to 2: load 1.9 per replica for 60 s*、*Draining replica 1: …*、*Removed replica 1 after draining for 74 s*），不記入稽核紀錄：不是人做的。目標和兩個時間（60 秒、10 分鐘）在 **進階** 裡。`/metrics` 有期望、就緒和排空中的副本數，以及負載。

## 對話中的圖片、音訊與影片

能讀圖片的模型（Qwen3-VL、Gemma 3 與 4 等）在 `/v1/chat/completions` 以 OpenAI 的內容區塊（content parts）接收圖片。模型能接受什麼，是在加入目錄時讀出來的：從它的 `config.json`，或 GGUF 模型的 **projector 檔**（`mmproj-*.gguf`，llama.cpp 要靠它才看得到圖片）。目錄會把它和授權一起列出。

- 圖片可以用 `data:` URI 送，也可以用 `https://` 網址：**閘道會自己下載**，再把資料轉給引擎。引擎從不自己下載任何東西，而且閘道只連公開位址，所以請求沒辦法讓你的伺服器去存取你自己的內部網路。
- 每個部署一次請求最多接受幾張圖片（預設 4 張）、影片要開啟才接受（預設關閉：開啟會在啟動時多占記憶體），請求大小也有上限（預設 64 MB）。這些都在部署表單的 **進階** 區塊，預設值就能用。
- 帶圖片、音訊或影片的請求只留在你自己的部署上，絕不送往雲端供應商。
- 用量會計算媒體項目數；圖片的 token 包含在提示 token 裡。

## 文字轉語音

語音模型以 `/v1/audio/speech`（OpenAI 的文字轉語音呼叫）回應音訊本身。三種引擎提供這項服務：

| 引擎（配方） | 在哪裡跑 | 模型 | 語言 |
|---|---|---|---|
| vLLM-Omni（`vllm-omni-tts`） | NVIDIA GPU | Qwen3-TTS CustomVoice：九種內建聲音，可下風格指示 | 中文（含各地方言）、英文和另外八種語言 |
| llama.cpp（`llama-cpp`） | AMD GPU 與 APU（Vulkan 或 ROCm）、NVIDIA、CPU | 附 projector 的 TTS GGUF：Qwen3-TTS、Chatterbox | Qwen3-TTS：中文、英文等；Chatterbox：英文 |
| speaches（`speaches-tts`） | CPU、NVIDIA | Kokoro-82M（51 種聲音）、Piper 聲音 | 英文（及其他拉丁字母語言） |

- 語音模型有自己的**聲音**（Playground 會列出來）。像 `alloy` 這類 OpenAI 聲音名稱會換成模型的預設聲音，回應會標明換成哪一個。
- **不提供聲音複製**：不接受參考錄音，也不能上傳聲音，只有模型原本就有的聲音能說話。
- 每個部署一次請求最多接受多少字元（*Longest input*，在 **進階** 裡）。預設值剛好是引擎一次說得完的量。
- 用量會計算說出的**字元數**與**音訊長度**。金鑰的每分鐘 token 數中，一個字元算一個 token。
- 語音只留在你自己的部署上，絕不送往雲端供應商。

## 圖片生成

圖片模型以 `/v1/images/generations`（OpenAI 的圖片呼叫）回應，圖片以 base64 傳回。兩種引擎提供這項服務：

| 引擎（配方） | 在哪裡跑 | 模型 |
|---|---|---|
| vLLM-Omni（`vllm-omni-image`） | NVIDIA GPU | diffusers pipeline（帶 `model_index.json` 的儲存庫）：Z-Image-Turbo、Stable Diffusion XL、FLUX.1-schnell、Qwen-Image |
| stable-diffusion.cpp（`sd-cpp`） | AMD GPU 與 APU（Vulkan）、NVIDIA（CUDA）、CPU（行程，不需要 Docker） | GGUF 或單一檔案：Stable Diffusion 1.5 / XL checkpoint，以及在同一個儲存庫裡、旁邊附有文字編碼器與 VAE 的 Z-Image 和 FLUX |

- **只有 base64。** Forgeyard 不保留它產生的圖片，所以給不出網址：`response_format: url` 會被拒絕。請解碼 `data[].b64_json`。
- **每個部署都有上限，各有能用的預設值：**一次請求最多幾張圖片（4）、最長邊（模型自己的：Stable Diffusion 1.5 為 512，其他為 1024）、最多幾步（50）。記憶體估算依這些上限計算，所以調高上限，估算也會跟著變大。
- **一次一個，其餘排隊。** 一張圖片在 GPU 上要幾秒，在 CPU 上要幾分鐘。一個副本一次只處理一個請求（*Requests at once*）；其他請求依序在閘道裡等待。佇列滿了，請求會得到 429 並附上 `Retry-After`。
- **授權。** 目錄會顯示每個模型的授權，以及它是否 gated。推薦清單只收 Apache-2.0 與 OpenRAIL 的模型；FLUX.1-dev、SD-Turbo 與 SD3.5 不在清單上（條款禁止商業使用或限制營收），但可以自己手動加入。OpenRAIL 授權的模型（SDXL、SD 1.5）可以商業使用，但授權禁止某些用途：它們的卡片會標出授權並附上連結，Gemma 與 Llama 也一樣。
- **不過濾提示。** Forgeyard 只檢查請求的格式與上限，不檢查它要求畫什麼。
- 用量會計算**圖片數**、它們的**千像素數**和**忙碌時間**（在 GPU 上即 GPU 時間）。
- 圖片只留在你自己的部署上，絕不送往雲端供應商。

## 影片生成

影片模型以 `/v1/videos`（OpenAI 的 Videos API）回應。一段影片要好幾分鐘，所以它是一個**工作（job）**：請求會立刻回應這個工作（`queued`），你輪詢它直到 `completed`（或 `failed`），再取回 MP4。由一種引擎提供：NVIDIA GPU 上的 vLLM-Omni（配方 `vllm-omni-video`），搭配 Wan 文字轉影片 pipeline（Wan2.1-T2V-1.3B、Wan2.2-TI2V-5B）。

- **工作只在一個副本上。** 閘道把它送到工作最少的就緒副本，之後只向那個副本詢問它的狀態和檔案。引擎把工作放在記憶體裡、檔案放在自己的磁碟上。
- **副本不在了，它的工作也跟著不在。** 副本被停止、搬移或刪除，或它的引擎重新啟動時，它的工作會回報 `failed` 並說明原因（`replica_gone`、`replica_restarted`、`video_lost`）：請重新要求。已完成的影片，若副本已不在，取內容時回應 410。
- **伺服器重新啟動時工作還在。** 它們存在伺服器的資料庫裡，副本也繼續工作；伺服器會重新接手。
- **結果會過期。** 完成的影片在部署的 *Keep results*（1,440 分鐘，一天）內可以取回；之後會在副本上刪除，取內容時回應 410。引擎自己也會在那之後一小時清掉舊檔，以防有刪除漏掉。
- **每個部署都有上限，各有能用的預設值：**最長的影片（5 秒）、最大的尺寸（模型自己的：Wan2.1 為 832x480，Wan2.2 為 1280x704）、等待中或製作中的工作數（8），其中單一金鑰的工作數（2），以及一個工作最多能花多久（一小時）。記憶體估算依最長、最大的影片計算。
- 1.3 **只支援文字轉影片**：圖片轉影片的參考輸入會被拒絕。
- **不保留提示**，而且一把金鑰只看得到自己的工作。
- 用量計算**每段影片一個請求**、它的**長度**和**忙碌時間**（GPU 時間）。
- 影片只留在你自己的部署上，絕不送往雲端供應商。

## 視覺模型

視覺模型（1.4）看一張圖片：**物件偵測**（方框、標籤和分數：RT-DETR、D-FINE、DETR…）、**影像分割**（一個點或一個方框所指東西的遮罩：SAM 2 和 2.1）和**深度估計**（每個像素有多近：Depth Anything、DPT…）。它們和其他模型一樣是模型種類：從 Hugging Face 加入目錄（推薦了三個）、部署後列在 **服務中 → 視覺**、在 **Playground** 試用（模型選單的 *Vision* 底下）、用 API 金鑰呼叫。

- **只有一種引擎，Forgeyard 自己的。** `vision` 配方在 `forgeyard-vision` 映像檔（和每個引擎一樣以 digest 固定）裡執行 Forgeyard 的視覺伺服器（PyTorch 上的 transformers）：NVIDIA GPU 上用 CUDA 版，以記憶體共用一張卡；任何機器都能用 CPU 版（AMD 機器用它的 CPU 執行：還沒有 ROCm 版）。模型和其他模型一樣來自機器的模型快取。
- **哪些模型：**目錄讀模型的 `config.json`。`…ForObjectDetection` 架構是偵測，SAM 2 是分割，`…ForDepthEstimation` 是深度；其他都不是視覺模型。**只接受寬鬆授權**（Apache-2.0、MIT、BSD）：Depth Anything V2 Base 和 Large（CC-BY-NC-4.0）以及 Ultralytics 的 YOLO 權重（AGPL-3.0）不能加入。
- **找你說的東西的偵測模型（1.4.4）：** 零樣本（開放詞彙）偵測模型（Grounding DINO、MM-Grounding-DINO、OWL-ViT、OWLv2）沒有固定的類別清單：每個請求說要找什麼（`labels: ["cat", "remote control"]`），同一個 `/v1/vision/detect` 就傳回這些名稱的方框。目錄標示 *Finds what you name*；它們需要 1.4.4 起的視覺映像檔。
- **圖片分類（1.4.4）：** 獨立的一種模型（任務 `image-classify`，在 `/v1/vision/classify`；文字分類是另一種）：固定類別的分類器（ViT、ConvNeXt V2、DINOv2：ImageNet 類別）回應自己類別中最符合的，零樣本分類器（CLIP、SigLIP 2）則在每個請求送來的 `labels` 中選。它們需要 1.4.4 起的視覺映像檔。
- **自己的 API：**`/v1/vision/detect`、`/v1/vision/segment` 和 `/v1/vision/depth`，每個請求一張圖片（multipart，或 JSON 裡的 base64），回應是 JSON；遮罩和深度圖是 base64 的 PNG。OpenAI SDK 沒有這個 API：任何 HTTP 用戶端都能呼叫。
- 每個副本**一次處理一張圖片**；其餘排隊等候。要更高吞吐量就多開副本。
- 用量計**每個請求一張圖片**、它的千像素數和忙碌時間。圖片只留在你自己的部署上：絕不送往雲端供應商，也不會被保存。

## 文字分類

文字分類模型（1.4.4）替一段文字從固定的一組標籤裡挑一個：情緒、語言、有害內容、主題。它是附有分類頭的小型編碼器（1 億到 6 億參數），所以在 GPU 上每秒能處理上千段文字，標籤和分數穩定，成本只有對話模型的一小部分。

- **一個引擎：**`vllm-pooling`（vLLM 的 pooling runner，和嵌入、重排序模型用同一個映像檔），在 NVIDIA GPU 上執行，以記憶體共用一張卡（同一個配方的 ROCm 版本應該也能在 AMD GPU 上執行，尚未測試）。目前還沒有 CPU 引擎：給 CPU 用的 transformers 引擎在 1.5（#144）。
- **哪些模型：**目錄會讀 `config.json`。vLLM 能當分類模型執行的架構（BERT、RoBERTa、XLM-RoBERTa、ModernBERT、GTE、GPT-2、Jamba：`…ForSequenceClassification`），而且有兩個以上標籤。標籤會存在目錄項目裡，顯示在模型的頁面上。不接受：只有一個輸出的模型（那是 reranker）、迴歸（regression）頭、零樣本（NLI）模型（標籤是 entailment 和 contradiction：請求裡要帶標籤，1.5 才支援），以及 DeBERTa、DistilBERT 或 BART 分類模型（vLLM 不支援；同樣在 1.5）。
- **它自己的 API：**`/v1/classify`，格式和 vLLM 一樣：`input` 是一段文字或一串文字；每段都會傳回最可能的 `label`，以及每個標籤的機率（`probs`，順序和 `config.json` 相同）。訓練成同時給多個標籤的模型（`multi_label_classification`，例如 toxic-bert）會各自評分每個標籤，所以機率加起來不一定是 1。
- **現在就想用自己的標籤：**對話模型已經能用結構化輸出分到你指定的任何標籤：在 `/v1/chat/completions` 把標籤放進 `structured_outputs.choice`（vLLM），或用 JSON schema 的 `enum`（vLLM、llama.cpp、雲端供應商）。比分類模型慢、成本也高，但不用另外部署。見[操作指南](how-to.md#classify-text)。
- 用量計它的 **prompt token**，和嵌入一樣。文字只留在你自己的部署上：絕不送往雲端供應商。

## API 金鑰、限制與用量

- 程式以 **API 金鑰**（`fyk_…`）呼叫 `/v1`。每個人都在 **API 金鑰** 建立自己的金鑰。金鑰只會顯示一次；伺服器只保留它的雜湊值。
- **API 金鑰** 的清單只列出還能用的金鑰。已撤銷和已過期的金鑰收在清單下方的一列 **顯示 N 把已撤銷的金鑰** 裡，*我的* 和 *所有人的* 都一樣；**Usage** 和 **稽核紀錄** 仍然會列出它們。*限制* 欄只顯示金鑰有設定的限制（「每分鐘 3 次請求」、「每分鐘 1萬 個 token」），沒有就是 *無限制*。
- 金鑰可以限制只能用某些模型、可以設定到期日，也可以設定**限制**：每分鐘請求數和每分鐘 token 數。超過限制時，閘道會回應 429 並附上 `Retry-After`。
- 管理員可以設定**預設值**（給沒有自己限制的金鑰）和**上限**（任何人能為自己的金鑰設定的最大值），也可以為任何人的金鑰設定限制。管理員為別人的金鑰設定的限制會被**鎖定**：金鑰的擁有者無法更改。
- 每把金鑰也有**雲端**設定，並可以有每月**預算**（見下方）。
- **Usage** 依日期、模型、金鑰、使用者、來源以及本機或雲端，統計請求數、錯誤數、token 數和延遲。每個人都看得到自己的；管理員看得到所有人的。它的 **Cost** 分頁顯示雲端請求的費用（見下方）。
- 圖表下方的表格依排序的欄位列出前 15 列（預設是請求數；**Cost** 分頁是費用；依日期分組時最新的日子在前）。其餘的加總成最後一列 *N others*，所以表格的加總仍和總數一致；**Show all N** 會列出每一列。點欄位標題就依該欄排序，再點一次則反過來排。在手機上每列只佔一行：名稱和排序所依的數字；點一下就展開其他欄位，順序用 **Sort by** 選。太長的名稱會被截斷：把游標移上去，或展開該列，就能看到完整名稱。
- 兩個分頁上的 **Over time** 會把其中一項數字畫成折線圖：按日（最近 30 天）、按週（13 週，從週一算起）或按月（12 個月），可以只看總數，或依金鑰、模型、供應商或個人（管理員選 **Everyone** 時）各畫一條線。最大的五條各自成線，其餘加總為 *Other*。把游標移到點上或用方向鍵可以讀出該期間的數值；**Show the numbers** 會以表格列出。日期以 UTC 計，最新的一期還在進行中（虛線）。

## 雲端供應商與分層

- **供應商**是 Forgeyard 以外的模型 API（OpenAI、Anthropic、Gemini、Azure OpenAI、OpenRouter，或你自己相容 OpenAI 的伺服器）。管理員連同金鑰一起新增；金鑰加密儲存，之後不會再顯示。
- `/v1` 上的每個模型名稱（在 API 裡）都是一條**路由**。路由有分成好幾**層**的**目標**：本機部署和供應商的模型。部署自己的路由一開始只有一層，就是這個部署。管理員可以在後面加上雲端模型，也就是部署的**雲端備援**，在它的頁面上設定。管理員也可以建立**雲端模型**：替供應商的模型取一個自己的名稱，在 **Cloud → Cloud models**。
- **本機優先。**只有在回答開始之前，而且本機這層無法使用、**忙碌**（每個副本都達到部署的 *Concurrent requests*）或回應 429 或 503 時，請求才會移到下一層。對本機 context 來說太長的提示，只有路由有設定時才會溢出。
- 每把 API 金鑰的**雲端**設定決定它的請求能不能離開你的網路：**永不**（預設值，1.2 以前的金鑰也都是）、**僅溢出時**，或 **允許**（也包括只有雲端的模型）。勾選 **僅本機** 的路由，以及帶著 `X-Forgeyard-Local-Only: 1` 的請求，也都不會離開。
- **雲端政策**（管理員在 **API 金鑰** 的選擇）是把兩個值合成一個：新金鑰拿到什麼，以及大家最多能給自己的金鑰什麼。*不使用雲端*、*個人可自行選擇溢出*、*預設溢出* 和 *允許雲端* 是常用的組合；*自訂* 會顯示兩個值。
- 供應商不是在**你的網路外**（要花錢，只有允許使用雲端的金鑰能用），就是在**網路內**（每把金鑰都能用，不套用預算）。新的供應商會依它的種類和位址預先勾好，由管理員確認。
- 回答會在 `X-Forgeyard-Target` 標明是誰提供的。Usage 會分開統計本機和雲端。

各供應商的細節請見[雲端供應商](cloud-providers.md)。

## 費用與預算

- **費用。** 每個請求在結束時計價一次。本機副本和你網路內的供應商費用是 0。雲端請求的費用是供應商回報的金額（OpenRouter 會回報），否則就是它的 token 數乘以供應商模型的**價格**（每百萬 token 的美元），價格由管理員輸入，或從 OpenRouter 的公開清單更新。模型沒有價格的雲端請求會算在 *without a price*，而不是算成 0。**Usage** → **Cost** 依日期、金鑰、個人、模型或供應商顯示費用。這是 Forgeyard 對供應商收費的估算，不是它們的帳單。
- **預算。** 預算是雲端請求每個日曆月（UTC）可以花的美元金額，可以設在 API 金鑰上（由擁有者設定，或由管理員設定並鎖定）、個人上（由管理員設定）或供應商上（由管理員設定）。請求送往雲端供應商之前，它最多可能花的費用會先對每個適用的預算**預留**；預算不夠時，請求就不會送往那個供應商。這時請求能留在本機就留在本機，只有在沒有其他目標能處理時，才會以 **402** 失敗。
- **警示。** 預算用到 80% 和 100% 時，Forgeyard 會在 **稽核紀錄** 寫一筆事件，並在 **API 金鑰**、**Usage** → **Cost** 和供應商的頁面顯示警告。

細節請見[費用與價格](cloud-providers.md#cost-and-prices)和[預算](cloud-providers.md#budgets)。

## 角色

| 角色 | 可以做的事 |
|---|---|
| `admin` | 所有事情：使用者、機器和它們的 GPU 存取權、模型目錄和引擎、雲端供應商和路由、稽核紀錄、所有人的金鑰、限制和雲端設定 |
| `operator` | 執行應用程式和部署模型；以及 user 能做的所有事 |
| `user` | 瀏覽各頁面、在 Playground 和用自己的 API 金鑰使用已部署的模型、查看自己的用量 |

**擁有者**是第一個帳號。它永遠是管理員，不能被降級、停用或刪除，所以沒有人能把管理權限鎖死。新加入的人會收到一個一次性連結，用來設定自己的密碼；除非設定 `REGISTRATION=approval`，否則不開放自行註冊。

## 登入與工作階段

- 密碼至少 12 個字元，常見的密碼會被拒絕。連續登入失敗時，之後每次嘗試都要等待（`LOGIN_FREE_FAILURES`、`LOGIN_IP_FAILURES`）。
- 工作階段在 2 小時沒有任何請求後結束，最長 7 天（`SESSION_IDLE_MINUTES`、`SESSION_MAX_DAYS`）。
- 在 **我的帳號**，你可以變更密碼（你的其他工作階段會被登出），並看到每個以你的身分登入的瀏覽器，每一個都可以登出。管理員可以在 **使用者** 讓某人在所有地方登出、停用他，或給他一個新的設定密碼連結。
- **稽核紀錄**（管理員）記錄登入、登入失敗，以及帳號、機器、模型、金鑰和供應商的變更，還有預算警示。
